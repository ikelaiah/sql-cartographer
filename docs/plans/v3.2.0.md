# SQL Cartographer v3.2.0 — Clear diagrams and guided exploration

**Status:** Implementation is complete and local automated gates pass. Manual
200% browser-zoom review and public publication are pending.

**Baseline:** v3.1.0. **Planning date:** 12 October 2026.

**Delivery:** [Implementation plan](../../tasks/plan.md) · [Task checklist](../../tasks/todo.md).

## Release promise

Help a developer open unfamiliar SQL, understand its shape, follow a finding
back to its source, and share a diagram they can explain with confidence.

| The project should be… | What v3.2.0 should deliver |
| --- | --- |
| Pleasant to read | Clear labels, calm toolbars, consistent words, and diagrams that open at a useful reading scale |
| Pleasant to use | A clear next action, predictable selection, reversible focus, and useful recovery from problems |
| Pleasant to learn from | Small named examples and explanations beside the evidence they describe |
| Pleasant to maintain | Small presentation modules, explicit interfaces, focused fixtures, and a contributor reading path |
| Wonderful to show other developers | Diagrams and exports whose typography, relationships, and uncertainty remain clear without the author narrating every detail |

Visual polish earns its place by helping someone understand the SQL. Accuracy,
traceability, and clarity are part of the visual design.

## Assumptions and scope

This proposal puts reading and exploration at the centre of the next minor
release. It keeps the existing browser runtime, four dialects, visual identity,
and explicit local storage. Existing v3.1.0 workspace, query, and ERD layout
files should work without migration.

The primary audience is a developer or DBA reviewing unfamiliar SQL. The
secondary audience is someone learning SQL relationships or contributing to
the analyser. Both Flowchart and ERD receive the same basic quality bar.

The five outcomes below are required. Broader parser coverage, a new rendering
engine, live database connections, framework migration, generated AI
explanations, and new SQL builder features are deferred. A reproduced
correctness bug discovered during this work can be fixed separately with its
own fixture and release evidence.

## What exists already

This proposal is grounded in source inspection and the checked-in v3.1.0
screenshots, rather than a new runtime usability study:

- [`src/app.ts`](../../src/app.ts) runs `fit()` after every Mermaid render.
  Fitting a tall chart into the whole canvas can reduce it to an overview when
  the user wants to read individual steps.
- Its `showDiagnostics()` joins messages into one warning string, discarding
  severity, code, and source location in the UI.
- Flow nodes already support source selection and object navigation. The next
  release should explain those nodes and make navigation intentional.
- [`src/samples.ts`](../../src/samples.ts) contains representative scripts,
  but the flow sample button chooses by dialect without explaining a lesson.
- ERD already has Find, a relationship inspector, orthogonal routing, layout
  controls, and join explanations. Improve these surfaces rather than adding
  competing controls.
- v3.1.0 already added diagrams, screenshots, a glossary, and a documentation
  map. The next learning improvement belongs inside the workflow as well as
  in a worked example.
- [`src/ui/erd-query-view.ts`](../../src/ui/erd-query-view.ts) separates DOM
  builders from stateful controllers. Follow that pattern for flow presentation
  and ERD card/inspector views.

## Required outcomes

### R1. A diagram that is readable on arrival

Open small diagrams in a useful composition. Open larger ones at a readable
scale with an explicit **Fit overview** action. Keep pan, zoom, direction, and
ERD layout controls available.

Selecting a flow step can highlight its immediate incoming and outgoing
relationships and frame that neighbourhood. **Clear focus** restores normal
presentation. These are statically modelled neighbours; this feature does not
claim to identify a runtime execution path.

Use consistent label wrapping, spacing, selected states, and contrast. Long
qualified names may wrap at meaningful boundaries; their complete identity
must remain available in the inspector. Provide a compact contextual legend
for the node provenance and relationship kinds present in the current view.
Use canonical exporter styles as the semantic reference.

**Acceptance:** At 1366 × 768 and 100% browser zoom, default reading views have
node labels at least 12 CSS pixels high on the agreed review fixtures. Explicit
overview mode may shrink them. Labels and directions are legible at reading
scale; long labels have a complete text alternative. Selection does not mutate
analysis, counts, exported semantics, or saved layout positions.

### R2. Select a step and understand the evidence

Add a flow inspector that answers: what is this step, where did it come from,
what connects to it, and what remains uncertain? Show node class, provenance,
available resolution metadata, and incoming/outgoing relationship kinds from
the existing graph. Explain synthetic nodes using their recorded reason.

Offer **Go to source** for valid spans and **Open object** for known workspace
objects. Grouped nodes expose all recorded spans. Selection opens context;
navigation is explicit so inspection does not unexpectedly replace the
editor's contents. Document this interaction change in the user guide.

Keyboard users reach the same information through labelled node controls or
an accessible node list if generated SVG navigation proves unreliable. ERD
retains its inspector and gains clearer key, cardinality, and join-row
explanations where needed.

**Acceptance:** Source, external, synthetic, grouped, and unresolved examples
each have a truthful explanation. Offered source actions select the correct
range in the correct input. Document-wide or unavailable evidence does not
receive a fabricated source link. Enter/Space and explicit navigation match
pointer behaviour.

### R3. Diagnostics that help the next action

Replace the wall of warning text with a short summary and expandable list.
Keep severity, stable code, message, scope, and available source location.
Provide **Go to source** where a valid span exists and a short next-step hint
for common codes, such as opaque SQL, ambiguous dialect detection, and missing
catalogue evidence. Unknown codes retain their original message.

Use the same presentation rules on both pages. Explain confidence, coverage,
and construct counts near their readout, including that they are not a
guarantee of semantic correctness. Distinguish errors, warnings, and
informational annotations through words and symbols as well as colour.

**Acceptance:** Multiple severities remain distinct; document-wide diagnostics
remain visible without fake locations; large lists do not cover primary
controls. Selection and filtering cannot alter underlying diagnostics or
health counts. Messages and user labels render as text, including hostile input.

### R4. Learn through four small examples

Replace anonymous sample loading with a small named chooser. Keep existing
representative dialect scripts as advanced examples. Add four introductory
lessons, each with a purpose, short explanation, and two or three inspection
steps:

| Lesson | Intended discovery |
| --- | --- |
| Follow a decision | Read an IF/ELSE branch and select its source |
| Follow data between steps | Distinguish control order from a proven temporary-table dependency |
| Read a query pipeline | Follow a CTE or derived query to its result |
| Understand a schema join | Read a declared foreign key, build a join, and inspect a row-multiplication note |

Lessons are curated local content attached to known samples. They do not
generate explanations for arbitrary SQL. Small flow lessons target at most
15 visible nodes; the schema lesson targets three to five tables. Each starts
in its intended view and dialect. Loading a sample must offer a cancellable
replacement action when input is non-empty, and never save automatically.

**Acceptance:** A first-time reviewer can choose a lesson, inspect its evidence,
and copy the relevant output using the page's instructions alone, within five
minutes in a recorded walkthrough. Cancelling replacement leaves input,
selected object, and stored work intact. Lessons never present unsupported
relationships as facts.

### R5. A codebase that explains how to extend the experience

Extract the presentation responsibilities needed by these features from
`src/app.ts` and `src/ui/erd-page.ts`. Controllers own state and events; view
builders and viewport calculations have typed inputs and outputs. Share small
diagnostic and lesson concepts where appropriate. Keep the two layout
algorithms separate because they operate on different models.

New pure presentation helpers join the strict TypeScript pilot. Keep global
loading order explicit, register runtime scripts in the packaging allowlist,
and rebuild generated output with source changes. Add a contributor walkthrough
from sample SQL to graph to selected-node explanation to export.

**Acceptance:** Pure helpers perform no analysis or storage writes. Refactors
change no graph, SQL, diagnostic, or export result. New responsibilities live
in bounded modules with documented loading order; controllers do not become
larger as this work lands. One reading path shows where to add a sample,
explanation, style, and regression fixture.

## Review fixtures and success evidence

The review sheet records five reproducible inputs: a small branch, the
existing realistic procedure, temporary-table dependencies, a report/dataset
chain, and an ERD with a long-name extension. The two available v3.1.0 images
are approximate before references, not paired captures of all five fixtures.
Candidate images and the review limits are in
[`v3.2.0-review.md`](v3.2.0-review.md).

Headless Chromium captures were reviewed at 1366 × 768 and 1920 × 1080, in
light and dark themes, for both pages. The 768 × 1024 stacked layout was
reviewed for both pages and themes; normal page scrolling keeps controls
reachable without page-level horizontal overflow. A real 200% browser-zoom
walkthrough and an independent developer review remain outstanding.

Reviewers should identify a branch, follow a relationship, find its source,
explain an uncertain finding, and share an export. Record completion, friction,
and limitations. Automated checks establish correctness; walkthroughs and
images establish whether the experience improved. Seek a second developer's
feedback when available and distinguish it from a maintainer walkthrough.

SVG and draw.io retain complete labels, graph facts, and provenance. Mermaid
retains semantic metadata and stable ordering. Temporary selection/dimming
must not leak into SVG downloads. Palettes may suit their medium; style
meanings must agree.

## Engineering contract

**Stack:** TypeScript 5.9.3 global scripts, HTML/CSS, vendored Mermaid, Biome
2.5.15, and existing Node/browser tools. No new runtime dependency is proposed.

| Location | Responsibility |
| --- | --- |
| `src/` | Analysis, models, and exporters |
| `src/ui/` | Controllers, DOM views, and browser helpers |
| `src/samples.ts` | Bundled SQL and curated lesson data |
| `tests/` | Semantic fixtures and browser interaction suites |
| `docs/plans/` and `tasks/` | Proposal, delivery plan, and checklist |
| `docs/releases/` | Evidence for shipped releases |
| `dist/` | Generated browser runtime committed with source changes |

Follow existing style. For example, `src/app.ts` guards and clamps source
ranges before selection:

```typescript
if(!span||span.start===undefined||span.end===undefined) return;
var start=Math.max(0,Math.min(sql.value.length,span.start));
var end=Math.max(start,Math.min(sql.value.length,span.end));
sql.focus();
sql.setSelectionRange(start,end);
```

Use named functions, explicit interface types, text-safe DOM builders, and
comments that explain evidence or constraints. Follow
[CONTRIBUTING.md](../../CONTRIBUTING.md) for change size, headers, and fixtures.

Implementation commands, run when relevant to the slice:

```text
npm run typecheck
npm run build
npm test -- --suite ui
npm test -- --suite erd-ui
npm test -- --suite security
npx tsc --project tsconfig.strict.json
python -m http.server 8000 --bind 127.0.0.1
```

Release qualification also runs `npm run lint`, `npm test`, `npm run test:file`,
`npm run metrics`, `npm run package:smoke`, and `npm run benchmark`. The task
checklist defines version-bump and metric-generation order.

Always preserve provenance, conservative semantics, deterministic outputs,
explicit persistence, escaping, and compatibility. Behaviour changes need
focused fixtures; visual changes need browser review. Review any dependency,
file-format, or semantic-contract change as a scope decision before implementing
it. Never invent relationships, introduce runtime network calls, silently save
input, or weaken a failing assertion to make a gate pass.

## Review decisions and release boundary

The maintainer review selected a top-right flow inspector, a 0.93 reading-scale
floor for 13px Mermaid labels, and four curated lessons. It retained explicit
overview, source navigation, local persistence, and conservative graph
semantics. Automated evidence and visual review are recorded in the review
sheet and candidate release note. No user study or independent review is
claimed. The public release remains pending until the review limits are
accepted and the repository can be committed and tagged.
